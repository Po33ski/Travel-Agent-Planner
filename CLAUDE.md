# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`README.md` is the detailed reference: infrastructure, every agent's behaviour rules, tools, the evaluation and clean-up. Keep it in sync when behaviour changes. This file covers what you need to work on the code.

`CHANGELOG.md` is the project log: why things changed, the decisions taken and what is still open. Before you start, read its latest entries. After a change to behaviour, configuration, infrastructure or the evaluation, add an entry at the top in the format given there. The file is git-ignored on purpose: it is a local log and is not part of the repository, so a fresh clone has none.

## What this is

A travel-planning assistant on **Azure AI Foundry Agent Service**, built in three variants so they can be compared:

- **Multi-agent (Magentic)**, in `agents/magentic/`: `managerAgent` (`gpt-5.6-luna`, no tools) plus four specialists on `gpt-5-mini`, each with exactly one tool: `ragDataAgent` (Foundry IQ MCP `knowledge_base_retrieve`), `webDataAgent` (`web_search`), `weatherAgent` (`get_forecast_weather`) and `hotelAgent` (`search_hotels_google_maps`). It keeps its own chat, `execution/agent_execution.py`, for comparison.
- **Single agent**: `travelAgent` in `agents/single_agent/`, with all four tools in one prompt. Only the evaluation uses it.
- **Concierge (agent as a tool)**: `conciergeAgent` (`gpt-5.6-luna`) in `agents/concierge/` leads a multi-turn conversation and has four subagents on `gpt-5-mini` as tools: `ragDataSubagent`, `webDataSubagent`, `weatherSubagent`, `hotelSubagent` (the team's data tools plus `ask_user`, with which each subagent asks the user about its own topic only). Its own chat is `execution/concierge_agent.py`, its evaluation `evaluation/concierge_agent_and_eval.py`. **This is the default chat**, and new work on the chat (memory, sign-in) targets it.

## Commands

The venv is `tutorials\` (git-ignored). The shell commands in `scripts/*.sh` use PowerShell backtick line continuation, despite the `.sh` extension.

```powershell
tutorials\Scripts\activate
pip install -r requirements.txt

# once, before the deployment: set up Microsoft Entra External ID in the Entra admin center (README, "Set up Microsoft Entra External ID"), then scripts/01_resource_deployment.sh
python utils/split_travel_guide.py                  # split inputs/world_city_travel_guide.md into inputs/travel_guide/ (git-ignored: on a fresh clone and after a change to the guide)
python rag/rag_setup.py                              # upload the guide, build the knowledge source and knowledge base (needs SOURCE_FOLDER_PATH = inputs/travel_guide, one file per city)
python agents/magentic/<name>_agent_deployment.py    # create or update the RAI policy and a new agent version
python agents/concierge/<name>_deployment.py         # concierge_agent and the four *_subagent scripts
python agents/single_agent/travel_agent_deployment.py
python execution/agent_execution.py                  # interactive chat (Magentic team)
python execution/concierge_agent.py                  # interactive chat (concierge with subagents)
python evaluation/magentic_exe_and_eval.py           # evaluate the team, report goes to outputs/
python evaluation/single_agent_exe_and_eval.py       # evaluate travelAgent
python evaluation/concierge_agent_and_eval.py        # evaluate the concierge (test conversations in inputs/concierge_evaluation_prompts.yaml)
```

- The runnable scripts are grouped by purpose: `execution/` (the two chats), `evaluation/` (the three evaluation scripts), `rag/` (knowledge base setup), `agents/` (agent deployment, one subfolder per variant: `magentic/`, `concierge/`, `single_agent/`). A deployment script in a subfolder finds the root with `Path(__file__).resolve().parent.parent.parent`. The project root holds only shared configuration (`config.yaml`, `requirements.txt`, `resource_deployment.bicep`) and `azure_app_config.md`, the hand-over for building the web app (what is configured in Azure and External ID, decisions, open items; keep it current when the infrastructure changes).
- Run the scripts **by path**. `python -m agents.…` breaks because the `openai-agents` package is also imported as `agents`. Every script outside the root adds the project root to `sys.path` itself, so `classes` and `utils` can be imported. The scripts in `execution/`, `evaluation/` and `rag/` also `os.chdir()` to the project root, because the relative paths they use (`config.yaml`, `inputs/`, `outputs/`, `SOURCE_FOLDER_PATH`) are relative to it; keep that block above the first `classes`/`utils` import in a new script there.
- There is no test suite, linter or build. The "tests" are the evaluation scripts. They call real models and the Foundry judge, so each case costs money. To run a subset, cut down `inputs/evaluation_prompts.yaml` or set `evaluation.evaluate_agents: false` in `config.yaml`.
- Every script needs `KEY_VAULT_URL` (set in the git-ignored `.vscode/launch.json`) and `az login`. All other settings and keys are Key Vault secrets, with one exception: `search_hotels_google_maps` still reads `GOOGLE_API_KEY` from the environment (the Key Vault version is commented out in `classes/google_services.py`). `launch.json` loads it from `.env` (`envFile`); outside the debugger, load `.env` into the environment yourself, or the hotel search returns "not configured" and every hotel case fails. A secret name is the setting name with `-` instead of `_` (for example `PROJECT-ENDPOINT`). `.env` holds the two third-party keys passed to the Bicep deployment; no Python code opens it.
- The concierge chat also signs the end user in, in the browser, through **Microsoft Entra External ID**: a separate customer tenant `travelplannercustomers.onmicrosoft.com` (authority `https://travelplannercustomers.ciamlogin.com/` in `sign_in` of `config.yaml`), user flow `travel-planner-last-flow` (sign-up with e-mail and password), public-client app registration `travel-planner-console` (redirect `http://localhost`, admin consent granted; client ID passed by `scripts/01_resource_deployment.sh` into the Key Vault secret `ENTRA-APP-CLIENT-ID`). It was set up in the Entra admin center, not by a script: `az login` works in the Azure tenant. That sign-in only selects whose memory is used (`oid` = partition key); Azure is still reached with `az login`, including Cosmos DB, which the concierge chat opens with Entra ID (data-plane role `Cosmos DB Built-in Data Contributor` from the template; the Magentic chat still uses the key).

## Architecture

- **Two halves of every agent.** The server-side definition (system prompt, tool schema, RAI policy) is created by `agents/<variant>/<agent>_deployment.py` from `agents/<variant>/<agent>_config.yaml` plus the `guardrails` section of `config.yaml`. The client side (`FoundryAgent` objects, Magentic workflow or `as_tool()` wiring, middleware, local tool functions) lives in the run scripts. Changing a prompt or a tool schema means running the deployment script again, because the deployment creates a new agent version.
- **Orchestration runs on the client.** `MagenticBuilder` (Microsoft Agent Framework) calls each Foundry agent through `FoundryAgent`. The agents never call each other. A new workflow is built for every user message, so there is no memory between messages.
- **Concierge** (`execution/concierge_agent.py`). Each subagent is a `FoundryAgent`; `subagent.as_tool()` (tool name = agent name, one string argument `task`) goes into the concierge's `tools`. `FoundryAgent` strips client tool declarations (the service rejects them next to an agent reference), so `agents/concierge/concierge_agent_deployment.py` declares the same four function tools server-side. A subagent sees only its task and starts a new conversation per call; the concierge keeps one `AgentSession` for the whole chat (service-stored history, updated only after a complete turn). Subagents ask the user through a local `ask_user` tool (`create_ask_user_tool()` in `classes/human_review_services.py`, `input()` behind a lock, because the concierge can run several subagents at once): child tool approvals cannot be resumed interactively through an `as_tool()` call in Python; the chat passes a list that logs every question and answer for the memory extraction.
- **Concierge memory** (`classes/user_sign_in_services.py`, `classes/user_memory_services.py`, `classes/memory_extraction_services.py`). Two Cosmos DB containers partitioned by `/userId` (= `oid`): `<prefix>-memory` with one `profile` item and one `trip` item per saved trip (TTL 365 days per item), `<prefix>-finetuning` with one item per chat (TTL 90 days). Small items instead of one growing document; the profile is written with an ETag check. `UserMemoryProvider` sends the note (`Travel history of this user:` + `Profile:` + trips with `past trip` / `upcoming or ongoing trip` / `dates unknown`) as a user message with the first message only, and marks it sent in `after_run`. At exit the chat is saved for fine-tuning, `MemoryExtractor` (`gpt-5-mini`, structured output `MemoryProposal`, prompt `concierge_memory.instructions`) proposes profile updates and trips, and only what the user accepts is saved. `/memory` and `/forget <n>|profile|all` are handled by the chat before the scope guard. The concierge chat does not use Azure AI Language. The Magentic chat keeps `CosmosMemory` + `TravelHistoryProvider` (one document per user, name-based login).
- **Function tools run locally.** `get_forecast_weather` and `search_hotels_google_maps` are `@tool` functions in `classes/weather_services.py` and `classes/google_services.py`. They are passed as `tools=[...]` to the `FoundryAgent`, which runs them when the server requests the call. MCP and web search run server-side. Tool functions return `{"error": ...}` instead of raising exceptions, so the agent can react to the error.
- **Middleware** (`utils/agent_middleware.py`) is attached to every agent. `drop_foreign_tool_contents` is required: without it, Magentic forwards other agents' tool calls and results, and Foundry rejects them with "No tool call found for function call output". `BlockedReplyMonitor` detects refusals and output-side content-filter cuts, which arrive without an error. `as_tool()` always streams the subagent, so `log_agent_replies`, `BlockedReplyMonitor`, `TokenUsageMiddleware` and `ConciergeCallRecorder` read a streaming run's final response through a result hook (`on_final_response`); keep that for any new middleware that reads `context.result`. The concierge's subagents need no `drop_foreign_tool_contents`; they get `add_todays_date_to_task` instead. `TokenUsageMiddleware` (`classes/evaluate_services.py`) is the only place that sees the manager's token usage.
- **Evaluation of the concierge** (`evaluate_concierge_test_case` and the other `*_concierge_*` methods of `EvaluateService`). One session per test case: scripted (`follow_ups`) or simulated (`user` with `goal` and `facts`: `UserSimulator`, `gpt-5-mini`, `user_simulator` in `config.yaml`, writes the next message or ends the conversation and answers the subagents' `ask_user`; its tokens are reported apart in `user_simulation`), every message through the scope guard with the previous reply. The conversation is judged by `concierge_answer_evaluators` (`per_turn` through `EvalItem.per_turn_items`, `whole_conversation` through `ConversationSplit.FULL`); `check_concierge_conversation` checks every reply's length and adds `goal_reached` for a simulated case. A subagent leaves no workflow events, so `ConciergeCallRecorder` records each call (dated task, streamed response) and each call is scored with the subagent's `agent_evaluators`; `conciergeAgent` itself is not judged as an agent (routing: `expected_agents`, replies: `concierge_answer_evaluators`).
- **Human in the loop** (chats only, `classes/human_review_services.py`). `enable_plan_review=True` makes Magentic stop after each plan, so `agent_execution.py` runs the workflow directly (`run_with_plan_review`, not `as_agent()`) and answers the `MagenticPlanReviewRequest` in the console. `hotelAgent` has a second local tool, `ask_user_about_hotels`, which asks the user with `input()`; the evaluation passes `approve_hotels_automatically` (same tool name, always approves) and builds the workflow without plan review.
- **Scope guard** (`classes/scope_guard_services.py`). Before the team, the single agent or the concierge runs, `ScopeGuard.check()` classifies the user's message with `gpt-5-mini` through `FoundryChatClient` (structured output, settings and prompt in `scope_guard` in `config.yaml`). An out-of-scope message gets `scope_guard.refusal` and no agent runs. Both chats and both evaluation scripts use it (`EvaluateService(scope_guard=...)`; its tokens are reported as `scopeGuard`). The concierge chat also passes `previous_reply` (the end of the concierge's last reply), so short answers such as "yes" are judged in context. It fails open on errors and re-raises `ChatClientContentFilterException`.
- **Tracing** (`utils/observability.py`). Each run script calls `enable_tracing()` once at the start of its async run; it calls `FoundryAgent.configure_azure_monitor()`, which reads the connection string from the project's Application Insights connection (`resource_deployment.bicep`) and sets up OpenTelemetry for the whole process. Settings and the per-script service names are in `observability` in `config.yaml`. Tracing must never stop a run: without the connection or the `azure-monitor-opentelemetry` package the script prints a `[TRACING]` line and goes on.
- **`add_todays_date`** (`utils/utils.py`) puts today's date in front of every task (for the concierge's subagents through the `add_todays_date_to_task` middleware, because they never see the user's message). The agents need it to resolve relative dates and the 15-day forecast window.
- **Classes** in `classes/` are thin service wrappers. Each takes its secrets through `SecretManager` (Key Vault with an in-memory cache).

## Things defined in more than one place (keep in sync)

- **Team wiring** (`FoundryAgent` names, descriptions, tools and middleware, and the Magentic limits) is duplicated in `agent_execution.py` and `magentic_exe_and_eval.py`. The single-agent wiring is in `single_agent_exe_and_eval.py`. Exceptions on purpose: only the chat attaches `TravelHistoryProvider` (`context_providers`) to the manager, because the evaluation has no user profile; only the chat enables plan review; the chat gives `hotelAgent` `ask_user_about_hotels`, the evaluation `approve_hotels_automatically`; each script passes its own key of `observability.service_names` to `enable_tracing()`. The concierge wiring is duplicated in `concierge_agent.py` and `concierge_agent_and_eval.py`. Exceptions on purpose: only the chat attaches `UserMemoryProvider` and gives the subagents the console `ask_user` (with the answers log); the evaluation gives them the simulated user's `ask_user` (`UserSimulator.create_ask_user_tool`) and adds `TokenUsageMiddleware` and `ConciergeCallRecorder` (after `add_todays_date_to_task`).
- **Travel history note**: the first line `Travel history of this user:` built in `classes/travel_history_provider.py` (Magentic) and the *Travel history* section of the manager's prompt; for the concierge, `NOTE_FIRST_LINE` and the labels in `classes/user_memory_services.py` and the *Travel history* section of the concierge's prompt.
- **Concierge memory fields**: `ProfileUpdates` / `TripMemory` in `classes/memory_extraction_services.py`, `PROFILE_LIST_FIELDS` / `PROFILE_TEXT_FIELDS` / `PROFILE_LABELS` in `classes/user_memory_services.py`, `concierge_memory.instructions` in `config.yaml` and the concierge's *Travel history* section. Changing the prompt means running `agents/concierge/concierge_agent_deployment.py` again.
- **Sign-in and Cosmos settings**: the External ID tenant in `sign_in.authority` (`config.yaml`) and the client ID of its app registration in `scripts/01_resource_deployment.sh` (`signInClientId`); the secrets `ENTRA-APP-CLIENT-ID`, `COSMOSDB-MEMORY-CONTAINER-NAME`, `COSMOSDB-FINETUNING-CONTAINER-NAME` in the Bicep template and `concierge_agent.py`.
- **Date line**: `TODAYS_DATE_PREFIX` / `add_todays_date` in `utils/utils.py` and the *Today's date* parts of the manager's, `travelAgent`'s, the concierge's and the subagents' prompts.
- **Agent names**: `agent_name` in `agents/magentic/*_config.yaml`, the `FoundryAgent` names in the run scripts, the *Team* section of the manager's prompt, `expected_agents` / `unexpected_agents` in `inputs/evaluation_prompts.yaml`, and the keys of `evaluation.agent_evaluators` in `config.yaml` (a missing agent is silently not evaluated). Concierge: `agent_name` in `agents/concierge/*_config.yaml`, the `FoundryAgent` names in `concierge_agent.py` and `concierge_agent_and_eval.py`, the tool names in `concierge_agent_deployment.py`, the *Specialists* section of the concierge's prompt, `expected_agents` / `unexpected_agents` in `inputs/concierge_evaluation_prompts.yaml` and the subagent keys of `evaluation.agent_evaluators`.
- **Function tool schemas**: the JSON `FunctionTool` schemas in `agents/magentic/weather_agent_deployment.py`, `agents/magentic/hotel_agent_deployment.py`, `agents/single_agent/travel_agent_deployment.py` and `agents/concierge/*_deployment.py` must match the parameter names of the Python `@tool` functions (`ask_user_about_hotels` has two implementations, `ask_user` a factory for the chat, both in `classes/human_review_services.py`, and `UserSimulator.create_ask_user_tool` for the evaluation in `classes/user_simulator_services.py`). The concierge's four subagent tools must match what `as_tool()` creates: the subagent's `agent_name` and one argument `task`.
- **Answer word limit**: the manager and single-agent system prompts, and `evaluation.max_answer_words` in `config.yaml`. The concierge has its own limit (300 words, a day-by-day plan 500; `max_answer_words.concierge` checks 500).
- **Out-of-scope refusal**: the exact sentence in the manager's, `travelAgent`'s and `conciergeAgent`'s system prompts, `scope_guard.refusal` in `config.yaml` and `expected_answer` of the `out_of_scope*` test cases (in both test files).
- **Concierge test requests**: the queries of the active cases in `inputs/concierge_evaluation_prompts.yaml` repeat those of `inputs/evaluation_prompts.yaml` (same ids), so the set-ups can be compared.
- **Infrastructure names**: `knowledgeBaseName` in `resource_deployment.bicep` must match the knowledge base that `rag_setup.py` creates. Key Vault secret names are defined in the Bicep template and read by the scripts.

`get_current_weather` is legacy: no agent uses it.
